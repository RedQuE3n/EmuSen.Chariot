Rendezvous and mailbox for Pegasus. Chariot never holds a note, never merges an
update, and cannot read a word either party writes.

**This release is MIT-licensed, and it is the same program.** Not one line of F#
changed between `v0.1.0` and `v0.2.0` — the diff is the `LICENSE` file, the
README, the design record, and one `PackageReference`. The protocol is untouched:
`Hello` still says **4**, so a 0.1.0 Pegasus and a 0.2.0 Chariot pair exactly as
before, in either combination.

## What changed

**The licence is now MIT.** v0.1.0 was GPL-3.0-or-later, and this repository was
the last link in a chain where no link was a decision: EmuSen chose GPL-3.0,
LunaP carried the term out of EmuSen without re-deciding it, Pegasus wrote that
its licence was "not a free choice", and Chariot said the same thing in the same
words about `EmuSen.Pegasus.Core`. Each of the others re-decided and found nothing
in its own dependency tree had been imposing copyleft either.

Chariot is a hard fork, so it had one extra question to answer, and
`docs/Chariot_Design.md` §11.2 answers it rather than leaving a reader to notice
it. Upstream — `cheshire-84/8BB-MSGR.NET` — carries **no licence at all**, which
cuts both ways: the fork rests on the offer described in §2 rather than on any
written term, and the GPL here was never inherited from upstream but added by us.
**Not one `.cs` file from the fork survives anywhere in the tree.** What this
repository distributes is entirely ours. The fork's first commit remains in the
history under no licence, and that is stated in §11.2 rather than glossed.

**The mechanical half is `EmuSen.Pegasus.Core` moving 0.2.2 → 0.3.0.** Core 0.2.x
is GPL-3.0-or-later on nuget.org, and a program cannot honestly put an MIT file
at its root while linking a GPL library, because the licence describes the work
as distributed and the distributed work would contain both. That bump is not
housekeeping beside the relicence; it *is* the relicence. Same wire, frame for
frame.

**The v0.1.0 binaries stay GPL-3.0-or-later.** A grant already made is not
withdrawn by a later, looser one, and source for them remains this repository at
the `v0.1.0` tag. A relicence is not a recall.

**The release is a workflow, and this repository had no CI before it.** §12.

## Running it

Chariot behaves like a daemon: options on the command line, the secret in the
environment, status on stdout, refusals on stderr, non-zero exit when it will not
start.

    CHARIOT_PASSPHRASE=your-secret ./EmuSen.Chariot --port 7420 --db chariot.db

| | |
|---|---|
| `--port N` | Listening port. Default **7420**. |
| `--db PATH` | Accounts and queued post. Default **`chariot.db`** in the working directory. |
| `--help` | Prints usage and exits **2**. |
| `CHARIOT_PASSPHRASE` | Required. No default, and it refuses to start without one. |
| `CHARIOT_HANDLE` | The name it signs in as. Default `chariot`. |

**The passphrase is not an argument on purpose**: anything in `argv` is visible
to every process on the machine through `ps`. Running it under systemd, the
network it needs, and where state is kept are all in
[`Pegasus_Setup.md`](https://github.com/RedQuE3n/EmuSen.Pegasus/blob/main/docs/Pegasus_Setup.md)
§6 and §7.

**The handle is fixed on first run.** Clients pin the key against the name, so
changing it later looks to every one of them like a new server.

## What was actually tested

Stated plainly, because a release note that implies more testing than happened is
worse than one that admits the gap.

- The suite passes: **20 tests**.
- **Every published binary was started on the platform it ships to**, by the
  release workflow, before it was uploaded. Each one was checked to print its
  usage and exit 2, to refuse to start with no `CHARIOT_PASSPHRASE`, and then to
  come up, open its accounts database and reach the listening line. That last
  check is the one worth having: `--help` never touches SQLite, so it is the only
  thing proving the native was carried into the single-file bundle and extracted
  — a missing native is invisible until a database is opened, and the first
  person to open one should not be you. §12.1.
- This is a real change from v0.1.0, whose macOS and Windows binaries were
  cross-compiled on Linux and had **never been run by anybody**.
- **The smoke test starts the server; it does not connect to it.** No client
  signs in, no frame crosses the wire, no note is relayed. The suite covers the
  protocol and it runs on Linux only.
- **Nobody has run a 0.2.0 relay in anger** on any platform. A runner started it
  and stopped it seconds later.
- **Nothing is signed or notarised**, so macOS and Windows will each object once
  and the checksum is the only integrity evidence there is.
- There is **no `linux-arm64` build**, so a Raspberry Pi cannot run this. Building
  from source on the machine is one `dotnet publish`.

## Upgrading

Replace the executable. Nothing writes a version into its state and there is no
migration on this line — no F# changed, so 0.2.0 reads an existing `chariot.db`
exactly as 0.1.0 left it. The protocol did not move, so an upgraded relay still
serves clients that have not upgraded.

## What it still will not do

Chariot **cannot read your notes**, and that is structural rather than a promise:
notes are sealed under a join code the relay never sees. The passphrase decides
who may open a session with the server; the join code decides who can read the
note. They are different secrets protecting different things — giving somebody
the passphrase lets them onto the relay, not into your notes.
`docs/Chariot_Design.md` §5 and §10.
